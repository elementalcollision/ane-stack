# PROBE-1: softmax-reduce family — h17 re-probe plan

**Lane:** L-PROBE  
**Status:** plan only — no edits, no hardware claims  
**Goal:** run the existing fuzzer's `softmax` / `reduce` generator against `h17` (M5) and diff against the recorded `h16g` baseline, producing both `docs/spec/ane-frontend-h17.md` and a machine-readable verdict matrix.

## 2. What the softmax-reduce generator produces today

`gen_softmax_reduce` (in `vendor/mil_spec/crates/mil_infer/src/fuzz.rs`) emits two sub-families, selected by `rng.below(2)`:

| kind | op | axis / axes | keep_dims | output shape vs input |
|------|----|-------------|-----------|----------------------|
| 0 | `softmax` | `axis = -1` (const int32) | N/A | same as input |
| 1 | `reduce_mean` | `axes = [1]` (const int32[1]) | `keep_dims = true` | same rank, channel dim = 1 |

Input tensor shape is `shape4(rng)` → one of 10 candidates, all 4-D `[N, C, W, 1]` with `N∈{1,2,4}`, `C∈{4,16,32,48,64,96,128}`, `W∈{1,2,4}`.

All cases are tagged `Expected::Valid` — the h16g matrix lists both ops as **OK**.

## 4. Execution steps (L-PROBE only)

### Step 1 — Run the fuzzer on h17
```bash
# From repo root (vendor/mil_spec is the crate root)
cd vendor/mil_spec
cargo build --release -p milc    # ensure milc binary is current
milc ane fuzz --iters 500 --seed 31337 --arch h17 -o /tmp/probe1_h17
```
- This uses the **existing** `gen_program` / `gen_softmax_reduce` logic unchanged.
- Output directories:
  - `/tmp/probe1_h17/cases/` — one subdir per case (`model.mil`, optional `weights/weight.bin`, `stdout.txt`, `stderr.txt`)
  - `/tmp/probe1_h17/findings/` — only cases where `class.is_finding()` (UnexpectedReject, UnexpectedAccept, Crash, Timeout)
  - `/tmp/probe1_h17/fuzz_report.jsonl` — one JSON line per case with `{id, family, expected, class, note}`

### Step 2 — Extract softmax/reduce subset
Filter the JSONL report for `family == "softmax"` or `family == "reduce"`. Expected count: ~500 × (1/6) × (1/2) × 2 ≈ **83 cases** (1/6 chance to hit the final `match` arm, 1/2 for softmax vs reduce, 2 sub-families).

### Step 3 — Diff against h16g baseline
For each softmax/reduce case, compare `h17_class` vs. `h16g_class` (which is `AcceptOk` for all). Three outcomes:
- **Same** (`AcceptOk` → `AcceptOk`) — no spec change
- **Regression** (`AcceptOk` → `UnexpectedReject` / `Crash` / `Timeout`) — h17 is stricter or buggy
- **Relaxation** (`AcceptOk` → `UnexpectedAccept`) — impossible for Valid cases, but tracked

## 8. Candid gaps (what the source material does not establish)

- **h17 availability:** The `ANE_FRONTEND_SPEC.md` table lists `h17` in the `TargetArchitecture` table, and `Anec::ARCHES` (in `anec.rs`) includes it. We assume the validator constructs on this M5. If `ANECValidate` returns `InvalidCompilationParam` for `h17`, the run will produce 500 `UnexpectedReject` — that is itself a finding.
- **Seed determinism across arch:** The fuzzer's `Rng` is a pure xorshift64*; the case *generation* is seed-deterministic. The *verdict* depends on the ANECompiler build. Same seed → same MIL corpus → valid cross-arch diff.
- **Compile vs validate:** The fuzz driver defaults to `--compile=false` (validate only). Adding `--compile` exercises `ANECCompile` too, which may surface additional failures (e.g., op-count limit). The plan uses validate-only for speed; a second `--compile` pass can be added later.
- **h16g baseline per-case data:** The fuzzer's JSONL report from the h16g run (seed 31337) is not committed in the repo. We will need to **re-run the same command on h16g** (or on a machine with h16g) to get the per-case baseline, or reconstruct it from the aggregate counts (336 accepts includes softmax/reduce). The plan assumes we can re-run on h16g; if not, the matrix will only have `h17` and the diff column will be "unknown".
