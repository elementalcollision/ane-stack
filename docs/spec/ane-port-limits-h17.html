ANE Resource Budgets

What one ANE program can hold on h17 (Apple M5 Max, macOS 26.7.1, build 25G241), re-measured 2026-10-22 and re-evaluated the same day. Every number below is asserted by docs/spec/ane-port-limits-h17.spec (124 probes, 274 assertions) unless it is tagged runner. Full text: docs/spec/ane-port-limits-h17.md.

The model in one paragraph. A program executes iff its live ports fit in 127. validate/compile additionally need its declared ports to fit in 255. Every state<> the program uses costs one port, and each returned update costs one more. Separately, each state surface owns one of the 55 BAR ids. In the packed layout (more than 55 sections) all non-state io shares at most two segments, data and const. So N_max = 55 − [any output] − [any plain input], for the asserted shapes, for fp16/int8 states (int16, uint8 and bool: dataset, docs/data/…/state_dtype_runs.jsonl), with inline or BLOBFILE weights (up to 8 MiB each, 32 tensors) and with LUT ops. Inside the compiled HWX, every task block ends with a flat trailer: 12-byte buffer bindings, whose slot word is a BAR ordinal or a special word below 0x2300, then 8-byte records.

1 · Ports — the execution cap

live_in + n_states + unique_out + n_exposed_states ≤ 127

Liveness roots are the returned outputs and every write_state. An input feeding only a state update still costs a port, even when the update is not returned. Dead inputs are free on the run path, and so are duplicate entries in the return tuple. Widening ports to 16 KiB does not move the boundary.

2 · Ports — the frontend cap

declared_in + n_states + out + n_exposed_states ≤ 255

validate and compile count declared inputs, dead ones included: (127, 128) is accepted, (128, 128) and (255, 1) are rejected, and 126 exposed states validate while 127 do not. The run path prunes dead inputs first, so the (255, 1) file still runs. Asserted on --arch h17. On h16g only the 128 + 128 rejection is asserted; the full sweep is runner. Note that validate/compile default to h16g.

Why the pool holds 55 is not known. Weights never take a BAR id of their own: all of them share one __KERN_0, which is kept only while an id is free (2026-10-26). An intermediate over about 2 MiB adds a __DATA scratch segment, which is not a BAR consumer runner.

4 · Inside the HWX — blocks and trailers

__TEXT.__text is a 0x10-byte preamble followed by a chain of blocks. Each block starts 16-byte aligned with [u16 idx][u16 size in u32 words] and ends with a flat descriptor trailer. Nothing is nested.

tagrolecount (gen_states-shaped programs with a plain input, outside the fan-out regime)
0x9344a task's primary sourceK + max(1, min(in, out)) — 54 at 53 states, 85 with 32/32 io, 1 with no update returned; ≥ 1 even when stateless
0x934aa further source of a binary task2 per self-add task on h17, 1 on h16g (32/32 io: 64 vs 32)
0x9442the task's destinationone per __data section, + one per intermediate spilled to __DATA scratch (52 states + 50 out → 154)

A slot word below 0x2300 binds a buffer that is not an __FVMLIB segment: 0x2080 is a fill or inline-constant source, and higher values bind the >2 MiB scratch runner. decode_slot_ordinals.py reports these as special=.

5 · State-copy records

tag = 0x9261 + 0x100·[dim1 ≠ 1] + 0x004·[dim0 field present] − 0x001·[dim1 = 16]

The low bits of the tag are presence flags (dim1 field, dim0 field, stride word), so the "read" 0x9361 and "write" 0x9365 records are the same record type. The dim0 field is present only in state-out records with dim0 ≠ 1; the update-row record never has one, but it still carries dim1 and the stride. A state with dim2 or dim3 exactly 256 emits no copy record. The dim3 case is asserted to still run; for dim2 that is runner.

The pitch column is read with decode_copy_words.py --last; [1,85,1,80] is asserted and the other rows are closed-form. The page rule is strong: 9 points are asserted and it fits 190+ shapes. State dtypes: fp16, int8 and bool are asserted to compile and run (int16 and uint8 runner); fp32 and int32 are rejected. The rule's ·2 assumes 2-byte fp16 elements. python3 scripts/state_exec_predict.py d0 d1 d2 d3 applies the rule.

7 · Planning rules

  1. Ports at execution: live_in + n_states + unique_out + n_exposed_states ≤ 127. Count every write_state as a root.
  2. Ports at the frontend: declared_in + n_states + out + n_exposed_states ≤ 255. Drop dead inputs first.
  3. States: N ≤ 55 − [any output] − [any plain input], which is 53 in practice, for every state dtype tried.
  4. State shape: d3 % 32 == 0 is always safe; otherwise ask the predictor.
  5. Return a state's update only if you need it, since each one costs a port. Never return an input unchanged.
  6. Pass --arch explicitly, and re-run the spec on any new OS build or SoC.

Not covered

  • Matmul or attention graphs, palettized or quantized weights, and multi-function programs. Every probe is an elementwise graph over rank-4 tensors; fp32/int32 ports and rank ≠ 4 are unmeasured.
  • The CoreML lane.
  • M4 silicon: h16g is cross-compiled only, and the M4 host is the only macOS 27.0 host.
  • Numerics: a pass means exit 0 plus a timing line. Runtime-position state appends are also untested.
