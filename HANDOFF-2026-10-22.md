## 1. What this project is

A vendored fork of [`savageAZfck/mil_spec`](https://github.com/savageAZfck/mil_spec) (© Adam Clark; upstream is MIT OR Apache-2.0 and the fork elects MIT, see `NOTICE` and `docs/LEGAL.md`). It reverse-engineers how to program Apple's Neural Engine directly, with no CoreML, no Python, and no Apple codegen where that can be avoided. The repo:
- hand-writes the CoreML `.mlpackage`/MIL format
- drives the private `ANECompiler.framework`
- executes via the private `e5rt` C API
- maps the ANE's internal resource model: io ports, the BAR pool, and the HWX records

**Attribution is a hard requirement.** Upstream is vendored at `vendor/mil_spec/`, pinned at `20f097f`. Keep `NOTICE`, `FORK.md`, and the in-file `FORK(ane-stack)` headers intact. Every change to the vendored tree is a numbered patch in `patches/`; the in-file `FORK(ane-stack)` comments are the change notices. The repo does not fully live up to this rule (see §4.3).

This is a public repo that drives private Apple frameworks. Read `docs/LEGAL.md` before shipping anything built here.

## 2. The one rule that governs everything here

**Evidence, not documentation.** Every claim must be reproducible by a command whose output is recorded, and asserted by a spec that re-runs it. A spec only counts if it **can fail**: judge pass/fail by exit code (`want_rc`) and anchor counts with `$` (see `docs/evidence/SPEC.md`).

This handoff's first version broke the rule. Its spec passed while five headline laws were false: a pass check matched the failure text, and the generators never varied the dimension that mattered. Don't repeat that mistake.

```sh
cd vendor/mil_spec && cargo build --release -p milc && cd ../..   # plain `cargo build` does NOT build milc
./scripts/evidence-check.sh docs/spec/ane-port-limits-h17.spec   # the master spec (builds milc itself too)
./scripts/evidence-check.sh --all                                # docs/evidence/*.spec AND docs/spec/*.spec (10 specs)
./scripts/apply-patches.sh --check                               # all 17 patches apply to pristine upstream (needs network)
./scripts/vendor-guard.sh --verify                               # vendored tree == manifest
bash tests/evidence-harness.sh                                   # the harness's own semantics (also in CI)
```

**What CI covers.** GitHub Actions runs `vendor-guard.yml` (tree vs manifest, patches apply, guard test, harness test) and `hw-skip-discipline.yml` (one test binary, `mil_infer --test ops_e2e`, with `xcrun` shadowed). **CI cannot run any hardware spec.** Nothing on GitHub protects the ANE laws; they're protected only by running the spec on an Apple-silicon Mac. Do that after every change.

### The ANE resource model (lane/probe) — re-measured 2026-10-22

The full writeup is `docs/spec/ane-port-limits-h17.md`. Every law there has a domain, a confidence label, and a spec section. In short, for one `main` function on h17, macOS 26.7.1:

| Budget | Law | Spec § |
|---|---|---|
| Execution io cap | `live_in + n_states + unique_out + n_exposed_states ≤ 127`, with no floor. Dead inputs and duplicate returns are free; the cap counts ports, not bytes. | 1, 3 |
| Frontend io cap | `declared_in + n_states + out + n_exposed_states ≤ 255` (`MaxLiveInLiveOutExceeded`); validate/compile count dead inputs | 2 |
| State cap = BAR pool | 55 BAR ids, one per `__FVMLIB` segment. Each state surface owns a segment, and non-state io packs into one data + one const segment. That gives **53 states** with a plain input and **54** without; one more fails with `unable to allocate free BAR` | 4 |
| Binding records | `0x9344` (primary source), `0x934a` (further source), `0x9442` (destination) are 12-byte records with slot word `0x2300 + 0x80·segment_ordinal`. `0x9344` is **not** a 54-entry state table. | 5 |
| Copy records | The tag is a presence-flag word (`0x9261 + 0x100·[dim1≠1] + 4·[dim0≠1] − [dim1=16]`); stride = `8·min(⌈log2 dim1⌉, 4)`; the update-row record carries the shape | 6 |
| State execution | 64 B row padding must not add a 16 KiB page, so with `d3 < 32` you need `d0·d1·d2 ≤ 256`. Only fp16 states compile. | 7 |
| h16g vs h17 | Same caps and laws; `0x934a` is emitted once per binary-add task on h16g and twice on h17; arch bytes differ in every record | 8 |

**What was wrong in the first version** (each item is now asserted the other way):
- an io "floor at 63"
- "53 states" as the cap itself
- a 54-record `0x9344` table ("WHY 54 resolved")
- a fixed `0x9361` read template
- stride `min(2·dim1+8, 32)`
- `0x9442` = 2N+1
- "one extra `0x934a` per program"
- a "constant payload 0x21"
- "53 states + 32/32 io" runs; it compiles but exceeds the execution cap

A scratch spec of the old model's predictions fails 9/9 on hardware.

## 4. The conventions you must follow

1. **A lane owns files, not features.** Read `docs/lanes/OWNERSHIP.md` and claim your lane before editing. Current claims:
   - **dave (initiator):** L-TOOL, L-TEST, L-PROBE, L-RUN, and **L-SCHED** (SCHED-1 → SCHED-4, with commits as recent as 2026-10-22).
   - **another model:** L-IR.
   - **unclaimed:** only **L-LINT**.

   Coordinate before touching L-SCHED or L-RUN files.
2. **Failing test first.** No behaviour change without a test that fails before and passes after. For a spec change, show the new line failing against the old model. Hardware-dependent Rust tests use `mil_compile::hw_gate`. Hardware specs use `require_hw`.
3. **Patches, not hand-edits, to `vendor/`.** Any change to the vendored tree needs:
   - a numbered patch in `patches/`
   - an entry in `PATCHES.md`
   - a row in FORK.md's modified-files table
   - a `FORK(ane-stack)` comment in the file
   - a regenerated `vendor/manifest.sha256`

   Derive the patch from a **committed** diff against pristine plus all lower-numbered patches (`PATCHES.md`, `docs/evidence/0006-double-patch-and-stacking.md`); in practice the manifest sync is a separate commit. Watch for these:
   - ⚠️ **`apply-patches.sh --rebuild` would delete 8 tracked files.** `crates/mil_infer/examples/{cml_exec,e5_dual_path,e5exec,mk_minflex,predseg,probe_run2_state,seg4,shape_flex_e5rt}.rs` were added without a patch, and `shape-flex-matrix.spec` builds them. `--rebuild` uses `rsync --delete`. Fix this first with a patch that adds them (see §5).
   - ⚠️ `vendor-guard.sh --generate` refuses a dirty tree **only when `.git` is a directory**. In a linked git worktree the check is silently skipped.
   - Only 9 of the 23 files touched by patches carry a `FORK(ane-stack)` marker, and FORK.md's table lists only 5 files.
4. **Upstream's `vendor/mil_spec/ANE_FRONTEND_SPEC.md`:** no hand-edits. Extensions go in `docs/spec/`. A *correction* to a measurably wrong upstream claim goes through the patch mechanism, as patch 0015 did (`OWNERSHIP.md` clarification). ADR-0002 A.6 still has a pending correction assigned to L-PROBE.
5. **Don't depend on the deploy lane on macOS 26.7.1.** `docs/adr/0002-deploy-lane-closed.md`: self-emitted HWX doesn't deploy there, and Apple's own artifacts fail too. Its Appendix A records that on **macOS 27.0** (one M4 Pro host) an h16g artifact loads and runs, and Apple's H16 bundles load. The decision still stands, but it's an OS-version statement. "Runs on the ANE" work targets the `e5rt` lane (`aned` compiles the MIL itself) or the CoreML lane.
6. **Fork-isolate every hardware probe.** ObjC exceptions abort the process, so run each probe as its own binary.
7. **Conventional commits:** `lane/<name>: <what>`. The body says what failed before, how it was verified, and the work-item ID. The work-item ID is the part most often missing; include it.

## 5. Open threads (where to continue, in priority order)

1. **Weights vs the BAR pool.** Does a weight segment (conv/matmul BLOBFILE) consume a BAR id? If it does, real models get fewer than 53 states; this decides the practical KV-cache budget. Blocked on getting a weighted program through `milc ane compile`: the BLOBFILE path doesn't resolve, and inline conv weights are rejected as `InvalidMILProgram`. Also open: why the pool is 55.
2. **Per-function and per-lane port caps.** Are 127 and 255 per function? Do multi-function programs and the CoreML lane share them? None of this is measured, and the scheduler needs it.
3. **State semantics and KV-cache shapes.** Open questions:
   - Does a `noupd` program persist state at runtime? This needs a read-back probe.
   - What do read-only states, multiple writes, and cross-state copies cost?
   - Do the page rule and port cost hold for `[1,H,S,D]` KV-cache layouts?
4. **M4 silicon.** All h16g data is cross-compiled. Run the spec's h16g items on an M4.
5. **Make `--rebuild` safe.** Add a patch (0018) that creates the 8 unpatched example files, then confirm `--rebuild` reproduces the tree byte for byte. Also clean up the other specs' weak assertions, which are L-TEST's: `0002` has no `want_rc`, `0004`/`0005` send `want_absent` output to `2>/dev/null`, and `0006-milc-json` and `shape-flex` depend on untracked `/tmp` artifacts (`/tmp/ir_fixed.compiled`, `/tmp/p3model`). `bash tests/evidence-harness.sh --lint docs/evidence/*.spec` lists the `run` lines with no `want_rc`.
6. **L-SCHED (claimed by dave — coordinate first).**
